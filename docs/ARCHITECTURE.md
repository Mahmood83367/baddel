# Architecture

```
shared/layouts/*.json      layout data (both platforms)
shared/fixtures/cases.json expected results (both platforms)

macos/Sources/BaddelCore   pure logic, Foundation only, no system APIs
macos/Sources/BaddelMacKit Accessibility, input sources, pasteboard, logging
macos/Sources/Baddel       menu bar app: hot key, Undo panel, windows
macos/Sources/BaddelAXCheck developer tool used by the check scripts

windows/src/Baddel.Core    C# port of BaddelCore
```

## Core (platform independent)

| Type | Role |
|---|---|
| `KeyboardLayout`, `LayoutStore` | Layout data: 47 keys, unshifted and shifted output, keyed by W3C key codes |
| `LayoutConverter` | Positional conversion between two layouts, on UTF-16 units |
| `ScriptEvidence` | Decides which layout text was typed on |
| `CorrectionPlanner` | Turns (text, target) into (range, replacement) or a rejection |
| `DoublePressDetector` | Single/double press state machine with injected time |
| `CorrectionEngine` | Checks, plan, write, verification, layout switch, guarded undo |
| `DiagnosticEvent` | A log record that can only hold codes, counts and flags |

The engine talks to the platform through three small protocols —
`EditableField`, `FocusProviding`, `LayoutSwitching` — so all of its safety
logic is unit-tested against simulated fields. The Windows app will implement
the same three interfaces on top of UI Automation.

The layout JSON is generated by `tools/dump-macos-layouts.swift`, which reads
the installed layouts with `UCKeyTranslate`. It reads layout tables only.

## The shortcut

`HotKeyCenter` registers one combination with Carbon's `RegisterEventHotKey`
and receives pressed and released events for that combination only. This needs
no Accessibility permission and gives Baddel no view of other typing.

A press that arrives without a release since the previous press is a held key
and is ignored. On the first press Baddel records which element has focus and
starts a timer; no text is read or changed yet. A second distinct press inside
the window runs a whole-field correction; otherwise the timer runs the single
correction. Either way the engine first checks that the recorded element is
still the focused one.

## Reading text

`AXField` wraps the focused `AXUIElement`:

- role and subrole decide whether it is a text field (`AXTextField`,
  `AXTextArea`, `AXComboBox`, `AXSearchField`) and whether it is secure
  (`AXSecureTextField`, never read);
- `AXValue` is the text, `AXSelectedTextRange` the selection or caret, both in
  UTF-16 units.

## Writing text

A write receives the full text the plan was made against. Before anything is
changed the field is read again: if it no longer holds that exact text, or the
range does not fit it, the write is refused (`fieldChanged` / `invalidRange`).
Strategies are then tried in order, and the field is re-read after each one:

1. **Ranged edit.** Set `AXSelectedTextRange` to the target range, read the
   range and the selected text back to confirm they are what was planned, then
   set `AXSelectedText`. Only the target range is touched; there is no
   select-all.
2. **Whole value.** Set `AXValue` to the full expected text.
3. **Paste fallback** (optional, off by default). After the same verified
   selection, the clipboard contents are saved, the replacement is placed on
   the clipboard marked as transient, and ⌘V is posted. Immediately before
   posting, Baddel checks again that this element still has system-wide focus,
   that its text is unchanged and that the selection is still the target range;
   otherwise nothing is pasted. The saved clipboard is restored afterwards
   unless something else has written to it in the meantime.

If the field ends up holding anything other than the expected text, the result
is `verificationFailed`: the layout is not switched and no Undo is offered.

## Layout switching

`InputSourceSwitcher` uses Text Input Sources. It only ever selects an input
source the user has already enabled, and it runs after the write has been
verified. The previously active source is remembered for Undo.

## Undo

The Undo panel is a borderless, non-activating `NSPanel` that cannot become key
or main, so clicking it leaves keyboard focus in the edited field. It is placed
just below the edited range (`AXBoundsForRange`); if the app reports no range
bounds, below the field's frame; if it reports no coordinates at all, at the
lower middle of the screen that has the pointer.

Undo runs only if the same element is still focused and still holds exactly the
post-correction text. It then restores the original text through the same
guarded write, restores the selection, and reselects the previous input source
if Baddel had switched it. The record is discarded when the panel disappears.

## Permissions

Baddel checks `AXIsProcessTrusted()` without prompting. The system prompt is
only shown when the user clicks **Request Access…** in Baddel's own window.
