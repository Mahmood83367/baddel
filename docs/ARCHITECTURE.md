# Architecture

```
shared/layouts/*.json        layout data (every platform)
shared/fixtures/cases.json   expected results (every platform)

macos/Sources/BaddelCore     pure logic: Foundation, plus CryptoKit for update signatures; no UI or system APIs
macos/Sources/BaddelMacKit   Accessibility, input sources, pasteboard, clipboard history, update check, logging
macos/Sources/Baddel         menu bar app: hot key, Undo panel, windows
macos/Sources/BaddelAXCheck  developer tool used by the check scripts

windows/src/Baddel.Core      the same pure logic in C# (no Windows dependency)
windows/src/Baddel.Windows   edit-control messages, UI Automation, input languages, clipboard, hot key
windows/src/Baddel.App       notification-area app: Undo popup, settings, About
windows/src/Baddel.WinCheck  developer tool: engine and app checks against a throwaway window
```

The sections below describe macOS first; [Windows](#windows) follows the same
design and is described at the end.

## Core (platform independent)

| Type | Role |
|---|---|
| `KeyboardLayout`, `LayoutStore` | Layout data: 47 keys, unshifted and shifted output, keyed by W3C key codes |
| `LayoutConverter` | Positional conversion between two layouts, on UTF-16 units |
| `ScriptEvidence` | Decides which layout text was typed on |
| `CorrectionPlanner` | Turns (text, target) into (range, replacement) or a rejection |
| `DoublePressDetector` | Single/double press state machine with injected time |
| `CorrectionEngine` | Checks, plan, write, verification, layout switch, guarded undo |
| `DiagnosticEvent` | A log record that can only hold codes, counts and flags |

The engine talks to the platform through three small protocols —
`EditableField`, `FocusProviding`, `LayoutSwitching` — so all of its safety
logic is unit-tested against simulated fields. The Windows app implements the
same three interfaces, and a Linux app will do the same on AT-SPI.

The macOS layout JSON is generated by `tools/dump-macos-layouts.swift`, which
reads the installed layouts with `UCKeyTranslate`. The Windows layout JSON is
generated by `baddel-wincheck --dump-layouts`, which reads the tables inside
the layout DLLs Windows registers (`KBDA1.DLL` for Arabic 101, `KBDA2.DLL` for
Arabic 102). Both read layout tables only, never keyboard input.

## The shortcut

`HotKeyCenter` registers one combination with Carbon's `RegisterEventHotKey`
and receives pressed and released events for that combination only. This needs
no Accessibility permission and gives Baddel no view of other typing.

A press that arrives without a release since the previous press is a held key
and is ignored. On the first press Baddel records which element has focus and
starts a timer; no text is read or changed yet. A second distinct press inside
the window runs a whole-field correction; otherwise the timer runs the single
correction. Either way the engine first checks that the recorded element is
still the focused one.

## Reading text

`AXField` wraps the focused `AXUIElement`:

- role and subrole decide whether it is a text field (`AXTextField`,
  `AXTextArea`, `AXComboBox`, `AXSearchField`) and whether it is secure
  (`AXSecureTextField`, never read);
- `AXValue` is the text, `AXSelectedTextRange` the selection or caret, both in
  UTF-16 units.

## Writing text

A write receives the full text the plan was made against. Before anything is
changed the field is read again: if it no longer holds that exact text, or the
range does not fit it, the write is refused (`fieldChanged` / `invalidRange`).
Strategies are then tried in order, and the field is re-read after each one:

1. **Ranged edit.** Set `AXSelectedTextRange` to the target range, read the
   range and the selected text back to confirm they are what was planned, then
   set `AXSelectedText`. Only the target range is touched; there is no
   select-all.
2. **Whole value.** Set `AXValue` to the full expected text.
3. **Paste fallback** (optional, off by default). After the same verified
   selection, the clipboard contents are saved, the replacement is placed on
   the clipboard marked as transient, and ⌘V is posted. Immediately before
   posting, Baddel checks again that this element still has system-wide focus,
   that its text is unchanged and that the selection is still the target range;
   otherwise nothing is pasted. The saved clipboard is restored afterwards
   unless something else has written to it in the meantime.

If the field ends up holding anything other than the expected text, the result
is `verificationFailed`: the layout is not switched and no Undo is offered.

## Layout switching

`InputSourceSwitcher` uses Text Input Sources. It only ever selects an input
source the user has already enabled, and it runs after the write has been
verified. The previously active source is remembered for Undo.

## Undo

The Undo panel is a borderless, non-activating `NSPanel` that cannot become key
or main, so clicking it leaves keyboard focus in the edited field. It is placed
just below the edited range (`AXBoundsForRange`); if the app reports no range
bounds, below the field's frame; if it reports no coordinates at all, at the
lower middle of the screen that has the pointer.

Undo runs only if the same element is still focused and still holds exactly the
post-correction text. It then restores the original text through the same
guarded write, restores the selection, and reselects the previous input source
if Baddel had switched it. The record is discarded when the panel disappears.

## Permissions

Baddel checks `AXIsProcessTrusted()` without prompting. The system prompt is
only shown when the user clicks **Request Access…** in Baddel's own window.

## Terminals

A terminal prompt is not an accessibility text field, so the shortcut path
above does not apply there. Instead the host hands over its own buffer:
`shared/shell/baddel.zsh`, `baddel.bash` and `baddel.ps1` are line-editor
widgets that pipe the command line to `baddel --fix-text` and put the answer
back, and Claude Code runs `baddel --fix-draft FILE` as its external editor.
Both commands are the packaged executable in a run-and-exit mode; they use
`TextFix` in the core (the same planner, plus cursor-unit conversion and the
Claude Code markers) and the app's layout settings. No keys are sent and no
screen is read; undo belongs to the host. See [the terminal guide](TERMINAL.md).

## Windows

The Windows app mirrors the macOS design; only the system APIs differ.

**Shortcut.** `HotKeyListener` registers one combination with `RegisterHotKey`
on a message-only window. Windows posts `WM_HOTKEY` only for that combination;
there is no keyboard hook. `MOD_NOREPEAT` makes Windows suppress auto-repeat,
so each notification is a distinct press, which is what the shared
double-press detector needs.

**Reading and writing text.** `FocusProvider` looks at the focused window of
the foreground thread and picks one of two implementations:

- `Win32EditField`, for standard edit controls (including frameworks that
  superclass them, and rich-edit controls while their content has no line
  break). Text is read with `WM_GETTEXT`, the selection with `EM_GETSEL`, both
  in UTF-16 units. A write selects exactly the target range with `EM_SETSEL`,
  reads the selection back, confirms the text is still the planned snapshot,
  and replaces the selection with `EM_REPLACESEL`, which the control records in
  its own undo buffer. `ES_PASSWORD` fields are secure and never read;
  `ES_READONLY` and disabled fields are unsupported.
- `UiaField`, for everything else, through UI Automation. The selection comes
  from the Text pattern and is only accepted when the text before it and the
  selected text line up exactly with the field's text. Single-line text is
  written through the Value pattern and verified; if a control reports
  something other than what was written, the snapshot is put back. Multi-line
  text is not written through the Value pattern, because controls disagree
  about line breaks; it needs the paste fallback or is refused untouched.
  `IsPassword` elements are secure.

Every write first checks that the field still holds the full text the plan was
made against, exactly as on macOS.

**Paste fallback** (off by default). The clipboard formats are copied aside,
the replacement is placed on the clipboard with the markers that keep it out of
clipboard history and cloud sync, and Ctrl+V is sent only after the shortcut's
modifier keys are released and a final check that the element still has focus,
unchanged text and the verified selection. The clipboard is restored unless
something else wrote to it meanwhile. Restoration covers the formats Windows
lets another process read back; exotic formats may be lost.

**Layout switching.** `InputLanguageSwitcher` reads the foreground thread's
input locale, posts `WM_INPUTLANGCHANGEREQUEST` for a layout the user already
has installed, and confirms the thread actually switched before reporting
success.

**Undo popup.** A borderless top-most window with `WS_EX_NOACTIVATE` that
answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`, so clicking Undo leaves focus
in the edited field. It is placed under the caret rectangle
(`GetGUIThreadInfo`, or the UI Automation selection bounds), else under the
field, else at the lower middle of the screen with the pointer.

**Threads.** The window message loop only handles the hot key and the popup.
Corrections run in order on one dedicated STA worker thread, which is where UI
Automation and the clipboard are used.

**Privileges.** The app runs as the invoking user (`asInvoker`) and never asks
for elevation, so it cannot edit windows of elevated programs; those attempts
are refused like any other unsupported field.
